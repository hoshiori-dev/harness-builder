# Proposal

Bootstrap change of this repository (`.agents/knowledge/spec-workflow.md`,
Bootstrap exception): approved in the conversation with the maintainer on
2026-10-29, before the pull request labels and the ruleset exist on the remote.

## Why

Projects that let coding agents work in them need a harness: an entrypoint,
knowledge the agent can reach, hard checks, an authority boundary, a
specification discipline, and a way to keep all of that from rotting. The
methodology for building one exists as a document; nothing yet turns it into
a procedure an agent can run in Claude Code, Codex, or Antigravity. The
existing public builders (the `meta` and `sdd` catalogs of another skill
library) carry machinery a plugin does not need (disposable markers,
platform-neutral vocabularies, two-phase extension slots) and predate the
revised methodology. This change ships the plugin that replaces them.

## What Changes

- Add two user-invoked entry skills: `harness-create` (greenfield and
  brownfield, told apart during investigation) and `harness-improve` (audit,
  repair, thinning, hardening, carrier or platform migration), each a
  self-contained workflow that confirms every decision with the user and
  presents recommendations rather than choosing.
- Add the methodology manual `harness-architecture`, which the entry skills
  and the builders load for the reasoning behind each layer.
- Add one builder per harness layer, each claiming its layer in its
  description so the entry skills route by description:
  `environment-building`, `knowledge-routing-building`,
  `hard-boundary-building`, `authority-building`,
  `spec-completion-building`, `entropy-building`, and the cross-layer
  `platform-lifecycle-building` (GitHub and GitLab as branches inside it).
- Add `project-skill-building`, which writes, improves, and diagnoses
  project skills for the target project and ships a Python skill linter.
- Add spec-driven development: the methodology skill
  `spec-driven-development` and three carriers, `openspec-workflow`,
  `spec-kit-workflow`, and `lightweight-spec-workflow`.
- Add the Claude Code agent `harness-verifier`, a read-only clean-context
  reader of a built harness.
- Every script and script asset the skills carry is Python with PEP 723
  metadata and a test; every skill is self-contained and names no other
  skill library.

## Capabilities

### New Capabilities
- `skill/harness-create`: entry; creates a harness for a project, greenfield or brownfield
- `skill/harness-improve`: entry; audits, repairs, thins, hardens, or migrates an existing harness
- `skill/harness-architecture`: the methodology manual the other skills load for reasoning
- `skill/environment-building`: the environment and sandbox layer
- `skill/knowledge-routing-building`: the knowledge and routing layer (entrypoint, knowledge files, scripts)
- `skill/project-skill-building`: writing, improving, and diagnosing a target project's skills
- `skill/hard-boundary-building`: the hard-boundary layer (pre-commit, CI, custom checks)
- `skill/authority-building`: the authority layer (policy, permission lists, checkpoint commits)
- `skill/spec-completion-building`: the specification and completion layer (level, carrier, gates, contract)
- `skill/entropy-building`: the entropy layer (sync rules, harness self-check, reclamation)
- `skill/platform-lifecycle-building`: the platform lifecycle layer on GitHub or GitLab
- `skill/spec-driven-development`: the SDD methodology and loop
- `skill/openspec-workflow`: the OpenSpec carrier and its platform automation
- `skill/spec-kit-workflow`: the Spec-Kit carrier and its platform automation
- `skill/lightweight-spec-workflow`: the SPEC.md / plan-mode carrier
- `agent/harness-verifier`: the read-only clean-context verifier for Claude Code

### Modified Capabilities
None.

## Impact

- Files: `skills/<name>/` for the fifteen skills, each with `SKILL.md`,
  `references/`, and where applicable `assets/` and `scripts/` (Python, each
  with a `_test.py`); `com.anthropic.claude-code/agents/harness-verifier.md`;
  `openspec/specs/skill/<name>/spec.md` and
  `openspec/specs/agent/harness-verifier/spec.md` through this change; both
  README skill tables; `.claude-plugin/plugin.json` regenerated by `just gen`
  (gains the `agents` pointer).
- Clients: every skill ships to Claude Code, Codex, and Antigravity; the
  agent ships to Claude Code only (Codex and Antigravity plugins carry no
  agents, `.agents/knowledge/compatibility-watch.md` W9 and W2).
- Dependencies: none added to the plugin; delivered scripts run on Python 3.10+
  with or without uv. The repository's checks gain Python files to lint and
  test (`just lint`, `just test`).
- Issue: none; bootstrap change.

## Acceptance

**Becomes true:**

- `just check` and `just clients-validate` pass with fifteen skills under
  `skills/` and one agent file; `.claude-plugin/plugin.json` lists the agent
  and no `mcpServers`.
- `/harness-create` and `/harness-improve` appear as user-invoked skills in
  Claude Code (`claude --plugin-dir .`), and no other skill does.
- Every `-building` skill's description carries `Owns the <layer> layer`
  with a layer from `scripts/lib/layers.ts` (`just skills-check`).
- Every delta spec's triggering and outcome scenarios pass when run through
  clean-context subagents as `.agents/knowledge/skill-quality.md` describes,
  with results recorded in the pull request.
- Running `/harness-create` against a scratch repository in the dev
  container produces an `AGENTS.md` within budget, reachable knowledge files,
  and a `check_harness.py` that passes there (the canary).
- Both README skill tables list all fifteen skills (`just harness-check`).

**Stays true:**

- No skill links outside its directory or names another skill library or an
  install command; every shared block equals the canon.
- The plugin ships no MCP server; `plugin.json` keeps its identity fields.
- Every delivered script is Python 3.10+ with PEP 723 metadata and a test;
  nothing under `skills/` requires Deno.
- The methodology document is not committed by this change; skills reference
  its sections by number only.
- The management code under `scripts/` stays Deno and is not called by any
  skill.
